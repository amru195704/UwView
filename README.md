## UwView は、ripgrep とも klogg とも同等の速さです。両方を1回で終えるので、通しでは約2倍になります。

**探すのは `ripgrep` と同等。開くのは `klogg` と同等。** 片方ずつ比べるなら、互角です。

でも、実際にやりたいのは「**探して、当たった場所を読む**」ことです。
`rg` で探して、当たりを見つけて、その場所を読むためにビューアで開き直す——**このとき、ファイルは2回読まれています。**
UwView は `uvf ファイル '語' -open` と打つだけで、**1回読むあいだに探して、そのまま画面に出す**ところまで終わります。

**これが約2倍の正体**です。速いアルゴリズムを見つけたからではなく、**読む回数が2回から1回になった**からです。

**51.25GB の1本のファイル**（Mac M4・外付け USB SSD・毎回キャッシュを捨てたコールド）

| やること | 相手 | 相手 | **UwView** | |
|---|---|---:|---:|:---:|
| **探す**（CLI・1語） | ripgrep 15.2.0 | 55.54秒 | **`uvf … -open` 50.74秒** | 同等 |
| **開く**（GUI） | klogg 24.11.0 | 52.55秒 | **50.44秒** | 同等 |
| **探して、画面で読むまで** | `rg` ＋ klogg | 108.1秒 | **`uvf … -open` 50.74秒** | **2.13倍** |

**1行目と3行目は、同じコマンドの同じ1回の実行です。** 探すだけの時間と、探して画面に出すまでの時間が、同じなのです。

**ここまで全部、無料版です。**

> `rg`＋klogg の 108.1秒は、実測2本（55.54秒・52.55秒）の足し算です。klogg 単体（開く＋検索）も 108.14秒。
> 語は `東京`（94,979件）。`uvf … -open` の 50.74秒は 51.25GB ÷ 50.74秒 ＝ **963 MB/s** で、このディスクを1回読み切る速度そのものです。
> **[条件と全データ →](https://uvp.y42u.net/benchmarks/)**

### サイズ別

| | 3GB | 10GB | 50GB |
|---|---:|---:|---:|
| ripgrep 15.2.0（探す・1語） | 3.29秒 | **11.38秒** | 55.54秒 |
| klogg 24.11.0（開く） | 3.65秒 | 10.98秒 | 52.55秒 |
| **UwView CLI（`uvf … -open`・探して画面へ渡す）** | **3.31秒** | **10.48秒** | **50.74秒** |
| **UwView GUI（開くだけ）** | **2.99秒** | **10.13秒** | **50.44秒** |

**どの行も、ファイルを1回読む時間そのもの**です。索引を持たない道具どうしなので、律速はディスクの読み出し速度になります。

**下2行を見比べてください。** 画面で**ただ開くだけ**が 50.44秒、コマンドで**探して画面に渡すまで**が 50.74秒。
差は **+0.32秒／+0.35秒／+0.30秒**——**ファイルが17倍になっても、探すぶんの上乗せは 0.3秒のまま**です。
読みながら探しているので、探索そのものには追加の読み込みが要りません。

**同じファイルに2回聞くと、3GB だけ ripgrep が勝ちます。** メモリに載る大きさなので2回目がキャッシュから返るためで、
検索7種を2回ずつ流した合計では 3GB が rg 32.30秒 対 `uvf` 33.31秒、10GB が 158.69秒 対 **147.01秒**、
50GB が 806.22秒 対 **735.97秒** でした。

> **Windows で `rg` を使っている方へ:** 50GB では `--no-mmap` を付けると **2.89倍**速くなります
> → **[検証記事](https://uvp.y42u.net/blog/uvp-rg-no-mmap-50gb/)**

## 使い方

```bash
uvf japan-latest.osm '東京' -open
```

**探し終えた瞬間に画面が開き、行番号つきの結果一覧が出ます。画面はもう一度探しません。**
**コマンドが終わってから一覧が出るまで 0.03〜0.08秒**です（3GB・10GB で 0.03秒、50GB で 0.08秒）。画面は、受け取った位置を並べるだけだからです。
あとは、前後の行を読む・一覧からジャンプする・複数キーワードを色分けする・条件を変えて探し直す——
調べる作業は、この行き来でできています。

**258.68GB・45億行**でも同じです。`uvf … -open` が **265.21秒**。
**klogg がこのファイルを開き終わるのに 258秒**かかります（差 7秒・2.8%）。

### UwView Pro — 2問目から桁が変わります

1問目は、klogg も `uvf` も `uvp` も、ファイル全体を1回は読まなければいけません。物理の話なので逃げ場がない。
違うのは**そのあと何が残るか**です。`uvp` は1回目に `.uwvz`（元の約 1/9・行索引つき）を作り、**2回目以降は元ファイルに触りません。**

**51.25GB に、2問目を投げたとき**

| | 開く | 検索 | 合計 | |
|---|---:|---:|---:|:---:|
| klogg 24.11.0 | 52.55秒（毎回作り直し） | 55.59秒 | 108.14秒 | |
| **`uvf … -open`**（無料） | — | — | **50.74秒** | 2.13倍 |
| **`uvp`**（`.uwvz` あり） | **0.01〜0.07秒** | **6.34秒** | **6.41秒** | **16.9倍** |

**klogg の 16.9倍、無料版 `uvf` の 7.9倍。** ここで初めて桁が変わります。
klogg は索引を残さないので**開くたびに作り直し**、`uvf` は索引を作らないので**2問目も1問目と同じ時間**。
`uvp` だけが、**1回目に払ったコストを2回目以降に回収**します。

**元ファイルを消しても検索でき、`-extract` で戻せます。** 51.25GB が約 5.7GB になります。

**1問目は無料の `uvf` が ripgrep と同程度で、`uvp` は `.uwvz` を作るぶん 15〜20% 遅くなります。**
**`uvp` が効くのは 10GB を超えて、同じファイルに2回以上聞くとき**です。

## 主な機能

**実測最大 258.68GB・45億行**（無料版で到達）／`uvf` コマンド（`-i`・`-E`・`-v`・grep 互換の終了コード・`-open`）／
**`.gz` をそのまま検索**（v1.6.6〜・下記）／検索結果一覧（元の行番号つき・ジャンプ・前後の文脈・保存）／
複数キーワードの色分け（32色・プリセット7種・`.uwvhl`）／文字コード自動判定（UTF-8・Shift-JIS・EUC-JP・UTF-16）／
リアルタイム Tail ／gzip を直接開く／マルチタブ・ブックマーク・横スクロール・セッション復元／全OS同一描画

**動作環境**: .NET 10 ／ Avalonia UI 12.x ／ Windows・macOS・Linux

### 🗜 `.gz` の検索は `zgrep` より速い（v1.6.6〜）

```bash
uvf app.log.gz 'ERROR'          # パイプを書かずに済む
uvf app.log.gz 'ERROR' -open    # 当たりをそのまま画面へ
```

展開処理を OS 標準の zlib に載せ替え、`gzip -dc | rg`（＝`zgrep` 相当）を**追い抜きました**。

| `.gz` を検索（コールド／ホット） | `gzip -dc \| rg` | **`uvf`** | 倍率 |
|---|---:|---:|---:|
| 3GB 相当（301MB の gz） | 1.18秒 / 1.16秒 | **1.16秒 / 1.00秒** | 1.02／1.16倍 |
| 10GB 相当（1.12GB の gz） | 4.38秒 / 4.29秒 | **3.66秒 / 3.38秒** | 1.20／1.27倍 |
| 50GB 相当（5.75GB の gz） | 22.06秒 / 21.71秒 | **17.20秒 / 17.04秒** | **1.28／1.27倍** |

`gzip` コマンドそのものより速いのは、**プロセス間のパイプを経由しない**ぶんです。

### 既知の制限：圧縮ファイル内の極端に長い行

`.gz` の中に **1行が 64MiB（ASCII で約6,700万文字）を超える行**があり、その行が検索に一致した場合、
「ファイルが壊れている」という趣旨のエラーになることがあります。**ファイル自体は壊れていません。**

**この制限は対応予定がありません。** ログや XML ダンプで 1 行が 64MiB を超えることは通常なく、
一方でこの制限を外すには行の長さに上限を置かない作りが必要で、**通常のファイルの処理まで遅くなります。**
UwView は「巨大なファイルを速く見る」ことに全振りした道具なので、**速度を優先します。**

該当するファイルは、`gunzip` で展開してから開いてください。
